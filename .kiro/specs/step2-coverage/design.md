# step2-coverage design

## Where the cases live
Fixed cases are `ObjectSpec.fixedCases` in the object's spec file (`src/conversions/specs-*.ts`), as for the seven pilot objects. The step 3 runner already runs fixed cases as regression cases, so a case added here also takes part in the next `convert` run of that object (step 3); pair records are not re-run just for that.

## Tranche A (no generator change)
The 20 pending objects whose only blocker (`unsupportedFeatures()`) is "no fixed cases", in batches, simplest first:
- **Batch 1, scalar functions without tables** (`specs-aw.ts`): `ufnGetAccountingStartDate`, `ufnGetAccountingEndDate` (the datetime literal and the 3.33 ms rounding), the three `CASE @Status` functions (`statusCases()`: every mapped value, 0, the first unmapped value above the last, 255, NULL), `ufnLeadingZeros` (padding, sign, 8 and 9 characters, int limits, NULL).
- **Batch 2 onwards:** `ufnGetContactInformation` and the AdventureWorks views (rows per table, written like `salesPersonCase()`: each row is there for a reason the label names), then the four WideWorldImporters `Integration.Get*Updates` procedures (cutoff boundaries, as `GetMovementUpdates`/`GetOrderUpdates`).

The four AdventureWorks scalar functions that fail step 4 come last and may be skipped: they stay failed whatever step 2 says.

## Negative control (`agreed-tests --negative-control`)
`corruptExpected()` copies the committed expected file in memory and corrupts case 1: the first non-NULL value is changed to another value of the same kind (text gains a suffix; numbers gain 1 in the integer part, keeping their scale; dates and timestamps move a year; bits flip; bytes change their first nibble), so it still loads into the same column type. State objects get the opposite outcome. With no non-NULL value, an extra all-NULL row is expected instead. The tSQLt and PostgreSQL scripts are generated from the corrupted copy and run; nothing is written to `tests/`, planted defects are not run, and step 2 is not recorded. The control is "seen failing" only if case 1 fails on both engines and every other case passes; the run writes `evidence/agreed-controls/<db>/<Object>.txt` and exits 1 otherwise.

Checked on two pilot objects before use (2026-11-18): `Sales.vSalesPerson` (value `n:1 -> n:2`) and `Website.ChangePassword` (outcome `completed -> raised`) both failed on both engines; no pair record changed.

## Schema-bound objects (batch 2)
`tSQLt.FakeTable` renames a table, and SQL Server refuses to rename a table that a `WITH SCHEMABINDING` object depends on ("cannot be renamed because the object participates in enforced dependencies"; seen 2026-11-18 on `Person.vStateProvinceCountryRegion` and `Production.vProductAndDescription`). `agreed-tests` detects `WITH SCHEMABINDING` in the source definition and passes `tsqltScript(..., { schemaBound: true })`: each test then empties the spec's tables with `DELETE` instead, inside tSQLt's test transaction, which tSQLt rolls back. A schema-bound object with state tests (which run outside that transaction) is refused rather than handled. Unit tests: `src/agreed/generate.test.ts`. Both views' negative controls were seen failing on this path.

## Finding: Person.vStateProvinceCountryRegion (batch 2, REQ-4.3)
Step 2 found a real difference that step 3 had passed. The view joins `CountryRegionCode` under the source collation `SQL_Latin1_General_CP1_CI_AS`: case-insensitive and blind to trailing spaces, so `'us'` joins `'US'` and `'CA '` joins `'CA'`. Kiro's draft used PostgreSQL `=`, which is neither; the generated data never produced codes that differ only in case or trailing spaces, so step 3 passed. The draft is kept as `conversions/AdventureWorks2025/Person.vStateProvinceCountryRegion.draft.sql` (the receipt shows it failing), the conversion now compares `rtrim(code)` under a nondeterministic case-insensitive ICU collation (`tsql_compat.ci_as_equal`), and the two failing cases stay as regression cases. Planted defects for each part of the fix (collation dropped from both sides, rtrim dropped, inner join made left) are caught by step 3 and by the agreed tests. A first version of the collation defect removed it from one side only, which is unobservable (an explicit collation on either side applies) and was replaced.

Batch 3 found the same difference in `Purchasing.vVendorWithAddresses` and `Sales.vStoreWithAddresses` (the same StateProvince–CountryRegion join), fixed the same way (`ciJoinFix()` in `specs-aw.ts` holds their planted defects and note).

Other objects may share the pattern: any join or comparison on text under a CI collation. The step 3 generator does not yet produce keys that differ only in case or trailing spaces; that is noted here, not fixed in this tranche.

## Tranche B: declared result errors
A spec's `resultErrorClasses` make a declared error an outcome, as in step 3 (`raisedAs` in `run.ts`). The capture records `raised: "raised: <class>"` for a case whose original T-SQL raised a declared error number (any other error stops the capture). Each generated test then asserts the outcome ("completed" or "raised: <class>"), and the rows only when it completed:
- tSQLt: `INSERT INTO #Actual EXEC ...` inside TRY/CATCH; only the declared numbers map to the class, any other error becomes "unexpected error N: ..." and fails the outcome assertion. The declared error dooms tSQLt's test transaction (tSQLt prints "Uncommitable transaction detected!" and rolls it back); the outcome assertion has already run and is what tSQLt reports (pass normally, "Failure: outcome" in the negative control).
- PostgreSQL: `pp_actual` is created `WITH NO DATA` (the call does not run), then a block inserts the call's rows and records "completed", with an exception handler for the declared SQLSTATEs only.
- Negative control: a raised case is corrupted to "completed with no rows". Seen failing for both bill-of-materials procedures (2026-11-18).

## Tranche B: geography and xml columns
- geography (points only, as in step 3): a fixed case writes WKT; the canonical cell is `g:POINT(x y)`. SQL Server gets `N'POINT (x y)'` (the `STAsText()` spelling; a string converts implicitly to geography, SRID 4326, on insert), PostgreSQL `'POINT(x y)'` (the `ST_AsText()` spelling). Result columns are already text (the views' calls use `STAsText()` / `ST_AsText()`). Fixed cases use binary-exact coordinates (-122.25, 47.5) so neither engine rounds them in the text.
- xml: documents are written in SQL Server's serialised form (empty elements as `<fax/>`) and travel as text. Neither engine compares xml: tSQLt holds xml result columns as `nvarchar(max)` and inserts them through an explicit `CONVERT(nvarchar(max), ...)` (xml does not convert implicitly; seen failing 2026-11-18); PostgreSQL selects them `::text`. An xml result from a procedure call (EXEC) is refused rather than handled.
- Targeted negative controls (`agreed-tests --negative-control --control-column <name>`: the first non-NULL value of that column is corrupted, so the new type itself is seen failing, not a neighbouring id): `Website.Customers` and `Website.Suppliers` on `DeliveryLocation` (a point moved by 1 along x), `HumanResources.vEmployee` on `AdditionalContactInfo` (the document's last character changed). Evidence: `evidence/agreed-controls/<db>/<Object>.<column>.txt`. `Sales.vIndividualCustomer`'s cases have `Demographics` NULL only, so its xml value path is not exercised (the type path is, by `vEmployee`); noted, not added.

## Finding extended to a verified object
The CI_AS CountryRegionCode join also appears in `HumanResources.vEmployee`, `Sales.vIndividualCustomer` and **`Sales.vSalesPerson`, which was verified on 2026-11-16**. `countryCodeVariants()` (`specs-aw.ts`) derives two regression cases from an object's existing case (province codes lowercased; with a trailing space), whose expected rows are the same. They failed on PostgreSQL for all three before the fix and pass after it (same fix, drafts kept, three planted defects caught by step 3 and the agreed tests). `Sales.vSalesPerson`'s step 5 was then reset to not-run: the review of 2026-11-16 covered the previous conversion, and the corrected code has not been reviewed. The note on the record says so; it is pending until the owner reviews it again.

No other conversion in the repository has this join (`grep 'CountryRegionCode" = '` over `conversions/*/*.sql`, drafts excluded, 2026-11-18).

## Tranche B: JSON results (blocked on SQL Server)
Built and kept: the capture joins a FOR JSON procedure's chunk rows into one document (as the harness does); the PostgreSQL script compares the function's result with it as `jsonb` (whitespace, escaping and object key order are not compared there; array order and values are; step 3 compares key order); the negative control corrupts a value inside the document so it stays valid JSON (`corruptJson`). The tSQLt side was written to capture through `tSQLt.ResultSetFilter`, because SQL Server refuses `INSERT ... EXEC` on a procedure that uses FOR JSON.

Measured 2026-11-18 on `Website.SearchForStockItems`: PostgreSQL passed all 7 cases; every SQL Server test failed with error 6549 inside `tSQLt.ResultSetFilter` (the FOR JSON restriction applies through it too). No other in-server way for a tSQLt test to observe the result was found: a loopback OPENROWSET needs a provider the Linux image lacks, and copying the procedure's query into the test would not test the original object. The ruling of 2026-11-12 says step 2 is tSQLt on SQL Server, so these objects are refused by `agreed-tests` (with the reason) until the owner rules. The step 2 failure the trial run recorded was a harness limit, not a conversion defect, and was reverted.

## Tranche C
Built 2026-11-18 for `Sequences.ReseedSequenceBeyondTableValues`: per-case setup (`spec.sampleSetup`, called with the fixed case's args and tables), `spec.sampleTeardown` (SQL Server only; PostgreSQL cases roll back), and state observation queries (`stateCheck.queries`; the capture records each query's columns and rows in `expected.json` under `queries`). A tSQLt state test now observes everything (outcome, state tables, queries), undoes the setup, and only then asserts, because tSQLt reports a persistent object left by a failed test against the next test. The negative control corrupts the first query value when a case has queries. Still not designed: table-valued parameters, identity columns, dependencies and memory-optimized tables (C). Each new feature gets unit tests in `src/agreed/` and its own negative control before a pass is trusted.
